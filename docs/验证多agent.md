建议下一步按这个顺序推进：

1. 先做端到端验证

在设置页配置至少两个模型：

- 强模型：用于 `knowledge_card`
- 快速模型：用于 `side_agent`、`teacher_guidance`

然后验证：

- 创建知识卡是否使用强模型
- 旁支问答是否使用快速模型
- 刷新后任务路由是否保留
- 切换 Provider 后路由是否隔离
- 未配置路由时是否使用默认模型

2. 提交当前代码

当前这一阶段已经完成，建议先提交：

```bash
git add backend contracts frontend/src docs/model-routing.md
git commit -m "feat: add task-based model routing"
```

不要把已有的 `docs/agent*.md` 一起提交，除非它们是你的本次修改。

3. 增加调用可观测性

下一步建议给每次 AI 调用记录：

```text
task
agent_id
provider
model
protocol
耗时
输入输出 token
是否降级
错误信息
```

否则后续无法判断模型路由是否真的提升了效果。

4. 完善失败和降级策略

建议明确：

- 课程生成失败：直接报错，不静默降级
- 旁支问答失败：可以尝试备用模型
- 结构化 JSON 失败：允许一次格式修复
- Provider 不支持某模型协议：提前提示
- OpenCode 免费模型：继续保留当前友好错误提示

5. 进入“教师教学闭环”

当前已经有白板、旁支、教师引导和知识卡推荐，下一步最有价值的是完善教师 Agent：

```text
进入章节
  → 教师引导
  → 用户阅读
  → 用户提问
  → 旁支回答
  → 教师诊断
  → 教师追问或总结
  → 用户笔记
```

重点是让教师 Agent 不只是生成一句话，而是能够根据用户问题决定：

- 是否需要追问
- 是否需要回到前置章节
- 是否需要推荐知识卡
- 是否需要总结当前章节
- 是否建议用户记录笔记

6. 再实现多角色旁支群聊

等单 Agent 任务路由稳定后，再实现：

```text
用户
  ↕
Director
  ├── 教师
  ├── 助教
  ├── 质疑者
  └── 好奇学生
```

这时现有的 `participant_ids`、`sender_id`、`mode`、`director_policy` 就可以继续复用，不需要推倒重来。

我建议现在马上做第 1 步和第 2 步：先验证任务路由，再提交当前阶段。之后进入“教师教学闭环”开发，比立即做多 Agent 群聊更能提升实际学习效果。
