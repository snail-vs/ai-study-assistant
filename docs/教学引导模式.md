
- 左侧：教学大纲
- 中间：当前知识卡白板
- 右侧：同学讨论
- 缺少：老师在学习过程中的实时引导

我建议把“老师引导”设计成中间白板底部的固定区域。

```text
┌──────────┬──────────────────────────┬──────────────┐
│ 教学大纲  │ 当前章节白板              │ 同学讨论      │
│          │                          │              │
│          │                          │              │
│          │                          │              │
│          ├──────────────────────────┤              │
│          │ 老师引导                  │              │
│          │ 老师发言内容              │              │
└──────────┴──────────────────────────┴──────────────┘
```

## 老师引导的定位

老师引导不是一个普通聊天会话，也不是白板正文的一部分，而是：

> 依附于当前章节的动态教学过程。

它负责：

- 帮助学生进入当前章节
- 提醒学生应该关注什么
- 解释当前内容和前后章节的关系
- 对旁支问题进行诊断和总结
- 在学生出现知识断层时给出学习建议
- 推动学生继续思考，而不是直接替学生完成学习

白板负责“展示知识”，老师引导负责“带着学生学习知识”。

## 进入章节时的行为

当用户切换章节时，底部老师区域自动生成一段简短引导：

```text
老师：
这一节我们先理解 Linux 进程为什么不是一个简单的程序，
重点关注它和资源隔离、进程状态之间的关系。
```

建议第一版控制在：

- 1～3句话
- 重点提醒
- 当前章节学习目标
- 不重复白板全文

如果用户再次进入已经学习过的章节，则优先展示之前保存的引导内容，不必每次重新生成。

## 旁支提问后的行为

当前流程可以调整为：

```text
学生提出问题
    ↓
旁支 Agent 回答问题
    ↓
诊断 Agent 判断问题类型和知识断层
    ↓
老师引导生成针对性回复
```

例如学生问：

```text
为什么容器里的进程编号和宿主机不一样？
```

旁支会话回答具体问题：

```text
这是因为 Linux namespace 为进程提供了不同的 PID 视图……
```

然后底部老师引导出现：

```text
老师：
这个问题实际上触及了“进程视图”和“进程隔离”的关系。
你刚才看到的现象不是容器重新创建了一个进程，
而是同一个进程在不同 namespace 中拥有不同的编号。

建议你回到“进程与 namespace”这张关联知识卡，
重点观察 PID namespace 如何改变进程的可见范围。
```

这样旁支回答问题，老师负责把问题重新接回主线学习路径。

## 底部区域的交互方式

建议老师区域支持三种状态：

### 1. 展开状态

显示完整的当前老师引导：

```text
老师引导
────────────────
这一节我们重点理解……
```

### 2. 收起状态

只显示一行：

```text
老师：这一节重点理解进程视图和 namespace 的关系……
```

这样不会长期占用白板空间。

### 3. 历史状态

点击“查看引导记录”，查看当前章节的教学过程：

```text
进入章节时
老师：这一节我们先理解……

针对旁支问题
老师：这个问题涉及 PID namespace……

学习建议
老师：建议继续了解……
```

第一版不需要做成完整聊天窗口，时间线展示即可。

## 老师引导和旁支会话的边界

这几个角色需要明确区分：

| 角色 | 主要职责 | 是否直接和用户持续对话 |
|---|---|---|
| 主 Agent | 生成课程和知识卡 | 否，主要负责课程内容 |
| 老师 Agent | 引导学习、总结、串联知识 | 通过底部引导区域发言 |
| 旁支 Agent | 回答用户具体问题 | 是，存在独立会话 |
| 诊断 Agent | 判断知识断层和问题类型 | 否，作为内部能力 |
| 用户笔记 | 用户主动记录理解 | 用户自己维护 |

尤其要避免让老师 Agent 和旁支 Agent 输出重复内容：

- 旁支 Agent：回答“这个问题是什么”
- 老师 Agent：说明“这个问题在整个学习过程中意味着什么”

## 老师引导的触发时机

第一版建议支持以下两个触发点：

### 进入章节

自动生成初始引导：

```text
trigger = section_enter
```

### 旁支回答完成后

根据问题诊断生成引导：

```text
trigger = side_question
sourceConversationId = xxx
```

暂时不建议每次学生发言都触发老师回复，否则会产生过多干扰。只有以下情况才触发：

- 发现知识断层
- 问题和当前章节高度相关
- 问题可能改变学习路径
- 旁支回答后需要重新总结
- 用户明确请求“老师再讲一下”

## 与知识卡的关系

知识卡本身建议分成两层数据：

```text
KnowledgeCard
├── sections                 静态白板章节
└── guidance                 动态老师引导记录
```

老师引导不应该直接修改白板正文，而是作为章节下的教学记录：

```text
知识卡
└── 第 2 节：进程与 namespace
    ├── 白板内容
    ├── 进入章节引导
    ├── 针对旁支问题的引导
    └── 学习建议
```

这样可以保证：

- 主线章节内容保持稳定
- 老师可以根据学习过程不断补充
- 刷新后能恢复完整教学过程
- 后续可以统计学生在哪些章节产生了疑问
- 关联知识卡仍然挂接在章节上，不破坏现有结构

## 推荐的第一版落地方案

第一版可以先实现一个轻量版本：

1. 白板底部增加“老师引导”区域。
2. 切换章节时生成一段章节引导。
3. 引导内容持久化到数据库。
4. 旁支回答结束后，如果诊断到知识断层，生成一段老师引导。
5. 老师引导显示“针对你的问题”标签。
6. 支持展开、收起和查看当前章节引导历史。
7. 不把老师引导混入旁支消息列表。
8. 不修改主线章节和白板内容。

最终形成这样的学习闭环：

```text
老师导入当前章节
    ↓
学生阅读白板
    ↓
学生在旁支提问
    ↓
旁支 Agent 回答
    ↓
诊断知识断层
    ↓
老师总结并重新连接主线
    ↓
学生记录笔记
    ↓
进入下一章节
```

这是比“白板 + 聊天”更完整的教学过程，也更符合你想要的“老师引导学习，同学讨论”的产品定位。
