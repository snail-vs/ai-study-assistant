结论先说：现在应该从“功能堆叠”转向“课堂节奏设计”。OpenMAIC 值得借鉴的是课程文档与运行时分离、先规划再生成、动作可执行；但 StudyCenter 当前最需要解决的，是固定产品语言、压缩 Agent 职责，并让每轮课堂交互足够克制。

当前旁支回答偏长还有一个直接的工程原因：真正流式回答时没有使用 `SIDE_AGENT_SYSTEM`，它只用于后面的断层诊断。实际答疑模型主要收到“根问题 + 当前问题”，因此“简洁回答”的 Prompt 约束没有真正作用于聊天回复。

## 一、先固定产品名称

我建议不再把“白板”和“旁支”作为一级用户语言。

| 现有叫法 | 固定名称 | 定义 |
|---|---|---|
| 学习空间 | 学习空间 | 围绕一个学习目标形成的内容和运行记录集合 |
| 主知识卡 | 当前知识卡 | 当前正在学习的知识卡，不赋予永久主从身份 |
| 关联知识卡 | 分支知识卡 | 从某个章节发现并创建的知识卡；首页中仍是普通知识卡 |
| 章节 | 章节 | 知识卡内部稳定的教学单元 |
| Markdown 白板 | 课程内容 | 当前章节的正式教学内容 |
| 老师引导 | 导师引导 | 帮助进入章节、提炼重点、讨论后回归主线 |
| 旁支会话 | 问题讨论 | 围绕一个具体问题形成的独立讨论线程 |
| 旁支 Agent | 答疑助教 | 直接回答当前问题 |
| 推荐知识卡 | 前置知识建议 | 诊断出知识断层后给出的学习建议 |
| 关联知识卡 | 学习分支 | 描述知识卡之间的学习关系，不是知识卡类型 |
| 主线 | 当前学习路径 | 运行时概念，表示用户从哪里来、学到哪里 |
| 互动版 | 互动讲解 | 需要图表、流程、模拟时临时切换的内容呈现方式 |
| 笔记 | 学习笔记 | 用户主动沉淀的个人理解 |

这里最重要的一点是：

> “问题讨论”只是讨论过程，只有用户确认创建知识卡之后，才形成“学习分支”。

不是每次提问都应该被称为旁支，也不是每张通过关联创建的卡永远都是“关联卡”。

## 二、固定页面区域

### 顶部：学习状态栏

显示：

```text
学习空间 / 当前知识卡 / 当前章节
```

右侧只保留：

```text
学习笔记｜主题｜设置
```

模型名称属于技术状态，建议弱化到设置或调试信息，不应长期占据课堂视觉中心。

### 左侧：学习导航

固定名称为“学习导航”，包含三组：

```text
章节目录
本节学习分支
前置知识建议
```

规则：

- 当前章节只展示挂接在本章节上的分支。
- 从首页打开知识卡时，它是独立知识卡。
- 从另一张卡的“本节学习分支”进入时，才显示“返回来源知识卡”。
- 不再使用“返回主知识卡”，因为 B 也可能是 A 的分支，同时又是 C 的来源。

### 中间：课程区

中间整体叫“课程区”，内部依次是：

```text
课程内容
章节导航
导师引导
```

“课程内容”目前使用 Markdown 渲染，未来可以切换为：

```text
文本讲解
互动讲解
测验
练习
总结
```

因此“白板”更适合作为未来某种 Renderer，不适合作为整个中间区域的产品名称。

### 右侧：讨论区

固定名称为“讨论区”，包含：

```text
讨论列表
当前问题讨论
输入框
```

按钮使用：

```text
＋ 新建讨论
```

不再显示“新旁支”。

每个问题创建一个讨论线程，可以继续追问，但不会污染其他问题。

### 抽屉：学习笔记

继续使用侧边抽屉，叫“学习笔记”。

笔记必须由用户主动创建，AI 可以建议记录，但不能自动替用户写入。

## 三、重新固定 Agent 职责

当前真正运行的 Agent 建议明确为五类：

| Agent | 是否对用户可见 | 职责 | 输出长度 |
|---|---:|---|---:|
| 课程设计 Agent | 否 | 规划知识卡标题、目标和章节结构 | 结构化 JSON |
| 内容生成 Agent | 否 | 生成当前章节课程内容 | 适中 |
| 课程导师 | 是 | 进入章节时引导；讨论后拉回当前章节 | 1～2 句话 |
| 答疑助教 | 是 | 回答当前讨论中的具体问题 | 默认 80～200 字 |
| 学习诊断器 | 否 | 判断知识断层并生成前置知识建议 | 结构化 JSON |
| 知识桥接器 | 是，但弱展示 | 从分支返回时解释与来源章节的关系 | 1 句话 |

课程设计 Agent 和内容生成 Agent 第一阶段可以仍由同一个模型承担，但概念和任务路由应分开。

当前注册的“好奇同学”“质疑同学”和 `group_director` 还只是框架：

- 运行时目前只取 `participant_ids[0]` 作为回答者。
- 好奇同学和质疑同学没有真正参与对话。
- Director 没有执行多轮角色调度。

因此现阶段不要在产品上称为“多 Agent 课堂”。等群聊模式真正实现后，再启用 Director。

## 四、旁支回答为什么会淹没课堂

当前链路实际上是：

```text
用户提问
→ 通用模型直接流式回答
→ 再调用 SideAgent 做断层诊断
→ 再调用课程导师总结
```

主要问题有三个：

1. 流式回答没有使用答疑助教 Prompt，长度不可控。
2. 答疑助教已经讲得很完整，课程导师又总结一次，产生重复。
3. 一个简单问题也可能返回标题、多个段落、列表、例子和总结，课堂节奏被打断。

应该改成：

```text
用户提问
→ 答疑助教给最小充分回答
→ 学习诊断器静默判断
→ 课程导师用一句话接回当前章节
→ 必要时展示前置知识建议
```

## 五、答疑助教的“克制输出”规则

默认回答不是“小文章”，而是课堂插话。

建议设定以下合同：

### 普通概念问题

```text
直接结论：1～2 句话
必要解释：最多 3 点
可选追问：1 句话
```

目标长度：80～160 字。

### 机制问题

```text
一句核心机制
最多 3 个步骤
一个与当前章节的连接
```

目标长度：120～220 字。

### 对比问题

最多使用 4 行表格，不做完整百科比较。

### 代码问题

只有用户明确要求时才输出完整代码，否则只给关键片段。

### 默认禁止

- 不重复用户问题。
- 不生成“总结”“结论”“深入分析”等多层标题。
- 不同时给出定义、历史、原理、案例、边界和扩展阅读。
- 不主动展开所有相关知识。
- 不用五六个列表项回答一个简单问题。
- 不在回答末尾连续提出多个问题。

如果用户需要更多内容，可以通过自然追问：

```text
展开解释
举个例子
换种说法
为什么
继续深入
```

这比一次性把所有信息倒出来更符合课堂节奏。

## 六、课程导师也必须克制

用户希望每次答疑后导师都拉回主线，这个行为可以保留，但导师不能再次回答问题。

导师只做两件事：

```text
这个问题和当前章节有什么关系
接下来应该带着什么结论继续学习
```

例如：

> 这里真正需要带回主线的是：容器并没有创造新进程，而是让同一个内核以不同视图管理进程。带着这个结论继续看 PID Namespace。

长度建议控制在 30～80 字。

导师不应：

- 复述助教答案；
- 再列三到五个知识点；
- 再举一个完整案例；
- 自动创建学习分支；
- 替用户写总结笔记。

## 七、断层推荐的触发标准

不是“提到了陌生概念”就推荐知识卡，而是满足以下条件之一：

- 不理解该概念会阻断当前章节；
- 需要超过当前回答预算才能讲清；
- 用户连续追问同一个基础概念；
- 当前问题明显属于更底层的独立主题。

推荐卡只显示：

```text
建议先了解：Linux 进程模型
原因：理解 PID Namespace 前，需要知道内核如何标识和管理进程。
```

用户可以：

```text
继续讨论
创建学习分支
删除
```

关闭弹窗只是隐藏，建议仍保留在左侧“前置知识建议”。

## 八、建议的教学闭环

```text
进入章节
→ 课程导师用一句话提示学习目标
→ 用户阅读课程内容
→ 用户发起问题讨论
→ 答疑助教给最小充分回答
→ 学习诊断器静默分析
→ 课程导师一句话拉回当前章节
→ 必要时出现前置知识建议
→ 用户决定继续主线或创建学习分支
→ 学完分支
→ 知识桥接器解释如何回到来源章节
```

## 九、实现优先级

第一步应立即处理：

1. 把流式答疑接入真正的答疑助教 System Prompt。
2. 将 `side_agent` 拆成 `side_answer` 和 `gap_diagnosis` 两个任务。
3. 答疑默认限制为 80～200 字、最多三个要点。
4. 导师引导限制为 30～80 字，并明确禁止重复答案。
5. 修改 UI 名称：课程内容、学习导航、讨论区、问题讨论、前置知识建议、返回来源知识卡。

第二步再做：

1. 主 Agent 拆成“课程设计”和“内容生成”。
2. 先生成章节规划，再按章节生成内容。
3. 给章节内容增加类型，为测验和互动讲解预留 Renderer。
4. 将学习路径、当前节点、来源节点和返回位置正式放入 Learning Runtime。

第三步才是多角色群聊和 Director。当前最有价值的不是增加更多角色，而是让现有三个可见角色——课程内容、答疑助教、课程导师——各自只说自己该说的话。
