这两个方向都值得做，而且可以把现在的“阅读课程”升级成完整的学习闭环。但需要先区分两类对象：

- 学习分支：补充或扩展“学什么”
- 学习活动：验证和应用“是否学会”

它们不应该混在同一个列表里。

## 一、知识分支不应只有“前置知识”

目前推荐知识卡主要解决知识断层，属于阻塞型关系。后续可以把学习分支明确分成三类：

| 类型 | 英文定义 | 目的 | 是否阻塞主线 |
|---|---|---|---|
| 前置知识 | `prerequisite` | 补齐理解当前内容必需的基础 | 可能阻塞 |
| 深入理解 | `deep_dive` | 解释当前概念背后的原理与细节 | 不阻塞 |
| 应用延展 | `application` | 展示实际应用、案例和迁移方向 | 不阻塞 |

例如学习“Linux 进程”：

- 前置知识：程序、CPU 执行、虚拟内存
- 深入理解：`task_struct`、调度器、进程状态转换
- 应用延展：容器隔离、进程监控、服务守护

产品上统一称为“学习分支”，但用简洁标签区分：

```text
学习分支
├─ [前置] Linux 虚拟内存基础
├─ [深入] task_struct 如何描述进程
└─ [应用] 容器如何隔离进程视图
```

其中只有“前置知识”需要强调“建议先学习”。深入和应用应该表现得更轻，不制造用户“主线还没学完又欠了很多内容”的压力。

数据上需要给推荐和关联关系增加：

```text
relation_type:
  prerequisite
  deep_dive
  application

necessity:
  required
  recommended
  optional
```

这样“为什么推荐”和“是否影响当前学习”就能表达清楚。

## 二、测试和实验属于“学习活动”

测试、练习、实验不是新的知识卡，而是挂在当前章节上的学习活动：

```text
知识卡
└─ 章节
   ├─ 课程内容
   ├─ 导师引导
   ├─ 学习活动
   │  ├─ 理解检查
   │  ├─ 应用练习
   │  └─ 动手实验
   └─ 学习分支
      ├─ 前置知识
      ├─ 深入理解
      └─ 应用延展
```

这个边界很重要：

- 点击学习分支：进入另一张知识卡，学习路径发生变化。
- 点击学习活动：仍停留在当前章节，只是切换课程区的内容形态。

## 三、左侧导航建议

可以在当前章节下展开二级区域：

```text
2. 进程的内核表示
   课程内容
   理解检查
   动手实验
   ─────────
   学习分支
   前置 · Linux 虚拟内存
   深入 · task_struct
```

顺序建议是：

1. 课程内容
2. 学习活动
3. 学习分支

因此你提出的“放在本节学习分支前面”是合理的。

不过不要让所有章节默认显示“测试、实验、练习”三个入口。由课程规划 Agent 判断该章节适合哪些活动：

- 概念章节：理解检查
- 操作型章节：练习或实验
- 对比型章节：分类、连线或判断
- 总结章节：综合测试
- 不适合实验的章节：不显示实验入口

这样左侧导航不会变得很重。

## 四、测试如何设计

第一版建议实现“理解检查”，而不是正式考试：

- 每次3～5题；
- 选择、判断、简答；
- 做完立即反馈；
- 不只是显示正确答案，还解释错误来源；
- 可以重新尝试；
- 测试结果允许触发前置知识建议。

完整流程：

```text
学习课程内容
→ 开始理解检查
→ Assessment Agent 批改
→ 判断掌握程度
→ 通过：建议进入下一节
→ 未通过：指出误区或推荐前置知识
```

这会让推荐知识卡更可信：它不再只根据用户提问推测断层，也可以根据答题表现判断。

## 五、实验入口放在哪里

实验放在左侧“学习活动”中是合适的，但建议同时在正文底部给一个上下文入口：

> 你已经了解进程创建过程，可以通过一个小实验观察 `fork()` 和 `execve()` 的行为。

按钮：

```text
开始实验
```

两个入口指向同一个实验：

- 左侧导航：方便回来继续；
- 正文底部：在最合适的教学时机出现。

不要把“生成实验”作为主要用户文案。用户关心的是“开始实验”，生成只是系统内部行为。第一次点击时再按需生成即可。

## 六、实验第一版不要做得太重

第一版可以是“指导式 Markdown 实验”，暂时不做在线容器和代码沙箱：

- 实验目标；
- 前置条件；
- 操作步骤；
- 命令或代码；
- 预期输出；
- 观察问题；
- 常见错误；
- 完成检查；
- 实验总结。

例如：

```text
实验：观察 fork 与 exec 的关系

1. 编译示例程序
2. 使用 strace 运行
3. 找到 clone、execve 系统调用
4. 回答：新程序从哪里开始执行？
```

后续再升级成真正的交互式终端、代码执行器或模拟器。

## 七、建议增加的领域模型

```text
LearningActivity
- id
- section_id
- type: quiz | practice | lab
- title
- objective
- status: suggested | generating | ready
- content_json
- generated_by
- created_at

ActivityAttempt
- id
- activity_id
- answers_json
- score
- mastery_level
- feedback
- started_at
- completed_at
```

课程规划 Agent 只负责决定：

```text
本节建议有 quiz
本节适合 lab
```

具体题目或实验内容在用户点击时按需生成，避免首次创建知识卡变得更慢。

## 八、Agent 分工建议

新增两个能力角色即可，不必马上做成可见聊天角色：

- `Assessment Agent`
  - 生成理解检查；
  - 批改答案；
  - 判断误区和掌握程度；
  - 将结果交给导师。

- `Lab Designer Agent`
  - 根据章节目标生成实验；
  - 给出步骤、验证点、提示和预期结果；
  - 保证实验与当前章节直接相关。

课程导师根据活动结果负责拉回教学主线：

> 你已经理解进程与程序的区别，但对 `fork()` 后地址空间的变化还有混淆。建议先回看第二部分，然后再进入下一节。

最终教学循环就变成：

```text
课程内容
→ 导师引导
→ 理解检查
→ 诊断
→ 必要时补前置分支
→ 应用练习或实验
→ 导师总结
→ 下一节
```

实施顺序建议：

1. 先增加分支关系类型：前置、深入、应用。
2. 实现“理解检查”和答题记录。
3. 增加 Markdown 指导式实验。
4. 最后再考虑在线代码执行、终端或互动模拟。

其中“理解检查”优先级最高，因为它能同时提升教学效果、知识断层诊断和导师引导质量。

----------

下一步不要同时做“知识延展、测试、实验”三条线。建议先做一个可验证的教学闭环：**理解检查 → 诊断 → 导师反馈 → 必要时推荐前置知识**。

## 推荐推进顺序

### 第一步：固定模型与产品规范

先补一份 `docs/learning-activities.md`，明确两套独立结构：

```text
学习分支 Learning Branch
- prerequisite：前置知识
- deep_dive：深入理解
- application：应用延展

学习活动 Learning Activity
- quiz：理解检查
- practice：应用练习
- lab：动手实验
```

同时明确：

- `section.contentType` 表示课程内容的主要呈现形式；
- `LearningActivity` 是挂在章节上的补充活动；
- 普通概念章节也可以同时挂一个 Quiz；
- 活动不会创建新知识卡，也不会改变主线位置。

### 第二步：实现“理解检查”最小闭环

这是下一项最值得直接开发的功能。

左侧当前章节显示：

```text
课程内容
理解检查
────────
学习分支
```

用户点击“理解检查”后：

1. 如果没有题目，按需生成3～5题；
2. 课程区切换到答题界面；
3. 用户提交答案；
4. Assessment Agent 批改；
5. 展示得分、逐题反馈和误区；
6. 课程导师给出一句总结；
7. 如果发现基础断层，生成前置知识建议；
8. 结果持久化，刷新后仍然存在。

第一版题型只做：

- 单选题；
- 判断题；
- 简短文本回答。

暂不做考试计时、题库管理、排名和证书。

### 第三步：增加分支关系类型

给推荐和关联知识卡增加：

```text
relationType
necessity
```

前端显示为简洁标签：

```text
前置 · Linux 进程模型
深入 · task_struct
应用 · 容器进程隔离
```

推荐产生策略也分开：

- 答疑或测试暴露基础断层 → `prerequisite`
- 用户追问底层原理 → `deep_dive`
- 学完章节后希望迁移应用 → `application`

深入和应用建议不需要像前置知识那样突出警告。

### 第四步：实现指导式实验

等 Quiz 闭环稳定后再做实验。第一版实验仍然使用 Markdown，不接代码沙箱：

- 实验目标；
- 环境要求；
- 操作步骤；
- 命令或代码；
- 预期结果；
- 检查点；
- 思考问题；
- 完成总结。

入口放在左侧“学习活动”里，同时在适合实验的课程正文底部显示“开始实验”。

## 建议的开发提交顺序

可以拆成四次独立提交，方便逐步验证：

1. `docs: define learning branches and activities`
2. `feat: add learning activity persistence and API`
3. `feat: add section quiz generation and attempts`
4. `feat: connect quiz diagnosis to mentor and prerequisites`

## 第一轮验收标准

完成后应能走通：

```text
打开某一章节
→ 点击理解检查
→ AI 生成题目
→ 用户答题并提交
→ 获得逐题反馈
→ 导师总结掌握情况
→ 必要时出现前置知识建议
→ 刷新后题目、答案和结果仍存在
→ 返回课程内容继续学习
```

所以现在最具体的下一步是：**先写学习分支与学习活动规范，然后实现 Quiz 的数据模型、接口和最小前端答题流程。**实验暂时只保留设计，不立即实施。
